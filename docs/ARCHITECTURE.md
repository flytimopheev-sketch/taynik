# Архитектура Тайника

Документ описывает устройство приложения: как устроено хранилище, как
проходит шифрование и какие решения приняты в каждом модуле.

## Общая схема

```
┌──────────────────────────────────────────────────────────────┐
│                          UI (GTK4)                           │
│  start_window · unlock_dialog · create_db_dialog             │
│  main_window · password_generator · passphrase_dialog        │
│  audit_dialog · settings_dialog · autotype · theme           │
└───────────────┬──────────────────────────────┬───────────────┘
                │                              │
         ┌──────▼──────┐               ┌───────▼────────┐
         │   models    │               │      db        │
         │ entry       │               │ crypto         │
         │ generator   │               │ schema         │
         │ passphrase  │               │ repository     │
         │ totp        │               │ io (CSV)       │
         │ audit       │               │ transfer (.taynik)│
         └─────────────┘               └───────┬────────┘
                                                │
                                        ┌───────▼────────┐
                                        │  SQLite (.rpwm)│
                                        └────────────────┘
```

Поток данных однонаправленный: UI → repository → SQLite. Модели не знают о
хранилище, криптография не знает о моделях.

## Хранилище

Файл `.rpwm` — обычная база SQLite (rusqlite, сборка `bundled`, то есть
встраиваемый SQLite без системной зависимости).

| Таблица | Столбцы | Назначение |
|---------|----------|-----------|
| `meta` | `key TEXT PK`, `value BLOB` | соль, параметры Argon2, verifier, версия схемы и формата шифрования |
| `entries` | `id`, `title`, `username`, `password`, `url`, `notes`, `tags`, `favorite`, `entry_group`, `color`, `totp`, `totp_params`, `created_at`, `updated_at` | записи; все значимые поля — BLOB |
| `entry_history` | `id`, `entry_id`, `password`, `changed_at` | прежние пароли записей |

Столбцы, которые не являются чувствительными (`id`, `favorite`, метки времени),
хранятся в открытом виде — они нужны для сортировки и фильтрации.

### Версионирование схемы

`meta.schema_version` хранится как 8 байт little-endian (`i64`).

| Версия | Изменение |
|--------|-----------|
| 1 | базовые записи |
| 2 | группы, цвета, TOTP-секреты, история паролей |
| 3 | параметры TOTP (`totp_params`) |

При открытии базы `migrate_schema()` добавляет недостающие столбцы через
`ALTER TABLE … ADD COLUMN` и обновляет версию. Миграции идемпотентны, поэтому
безопасно запускать их при каждом открытии.

## Криптография

### Вывод ключа

Мастер-пароль → **Argon2id** (memory 64 МиБ, iterations 3, parallelism 4) →
32-байтовый ключ AES-256.

Параметры и соль лежат в `meta` в открытом виде: они нужны для повторного
вывода ключа и не являются секретом.

Соль (32 байта) генерируется через `rand::thread_rng()` — CSPRNG из
популярного крейта `rand`, а не `std::collections::HashMap`-эндропия.

### Проверка мастер-пароля

Вместо самого пароля в базе лежит **verifier** — зашифрованная строка
`"taynik-verifier-v1"`. При открытии:

1. Из `meta` читаются соль и параметры Argon2.
2. Выводится ключ.
3. Расшифровывается verifier и сверяется с эталоном.

Неверный пароль и повреждённый файл дают разные результаты: расшифровка
не проходит → `WrongPassword`.

Для совместимости поддерживается «legacy»-verifier из баз, созданных до
переименования проекта.

### Шифрование полей

Формат зашифрованного значения:

```
nonce (12 байт) || ciphertext || tag (16 байт)
```

AES-256-GCM, уникальный nonce на каждое шифрование (важно: повторное
использование nonce с тем же ключом ломает аутентификацию GCM).

### Привязка к полю (AAD)

Начиная с версии 1.2.0 в качестве AAD (дополнительных аутентифицируемых
данных) передаётся имя поля: `title`, `password`, `totp` и так далее.

Что это даёт: если злоумышленник получает доступ к файлу базы, он не может
переставить шифротексты между столбцами. Например, подставив шифротекст
пароля в столбец `title`, он не сможет его расшифровать — GCM проверит AAD и
отклонит данные. Без AAD подмена прошла бы незаметно, а пользователь увидел
бы в поле «название» свой пароль.

Формат версионируется через `meta.blob_format`:

| Значение | Формат |
|----------|--------|
| отсутствует | 1 — без AAD (базы версий до 1.2.0) |
| 2 | с AAD |

`migrate_blob_format()` при первом открытии старой базы перешифровывает все
поля и историю в одной транзакции и только затем записывает `blob_format = 2`.
Если транзакция не завершилась, база остаётся в старом формате и продолжает
работать.

### Очистка памяти

`CryptoKey` реализует `Drop` с `zeroize`. Поле ключа приватное — его нельзя
случайно вывести в лог. Копия мастер-пароля, передаваемая в KDF, обёрнута в
`Zeroizing` и обнуляется сразу после вывода ключа.

## Смена мастер-пароля

Операция выполняется в одной транзакции:

1. Проверяется старый пароль (расшифровка verifier).
2. Генерируется новая соль, выводится новый ключ.
3. Все записи и история паролей перешифровываются новым ключом.
4. Обновляются соль и verifier.
5. Транзакция фиксируется, ключ в памяти заменяется.

Любая ошибка на любом шаге откатывает всё изменение — база остаётся в
прежнем состоянии и открывается старым паролем.

## Генераторы

### Пароли

`models/generator.rs` — наборы символов, минимальные количества цифр и
спецсимволов, перемешивание Фишера–Йетса, оценка стойкости по длине и
разнообразию символов (`len × log₂(алфавит)`).

### Парольные фразы

`models/passphrase.rs` — словарь из 1024 слов (`resources/wordlist.txt`,
встраивается на этапе сборки через `include_str!`). 10 бит энтропии на слово:
6 слов ≈ 60 бит, 8 слов ≈ 80 бит. Слова выбираются равномерно, поэтому
перебор по словарю бессмысленен.

### TOTP

`models/totp.rs` — реализация RFC 6238:

- SHA-1 (по умолчанию) и SHA-256 — обе реализации написаны вручную, чтобы не
  тянуть внешние криптографические крейты и сохранить полностью офлайн-характер
  приложения;
- HMAC по RFC 2104;
- динамическое усечение по RFC 4226;
- произвольное число цифр (6 или 8) и период;
- разбор ссылок `otpauth://totp/…` с извлечением `secret`, `issuer`,
  `algorithm`, `digits`, `period`.

Корректность проверяется эталонными векторами RFC 2202 (HMAC-SHA1),
RFC 4231 (HMAC-SHA256) и RFC 6238 (TOTP).

## Аудит безопасности

`models/audit.rs` анализирует расшифрованный список записей и находит:

- **слабые** пароли — по эвристике стойкости;
- **повторяющиеся** — один и тот же пароль в нескольких записях;
- **устаревшие** — не менялись дольше заданного срока (по умолчанию год).

## Форматы переноса данных

### CSV

`db/io.rs` — текстовый формат для совместимости. Пароли сохраняются **в
открытом виде**, поэтому UI всегда предупреждает перед экспортом. Файл
защищён паролем только на уровне прав доступа к файловой системе.

### `.taynik`

`db/transfer.rs` — собственный зашифрованный формат:

```
magic       8 байт  "TAYNKEXP"
version     1 байт
salt       32 байта
params     12 байт  (memory_kib, iterations, parallelism — u32 LE)
nonce      12 байт
length      4 байта (u32 LE)
ciphertext  AES-256-GCM, AAD = "taynik.export.v1"
```

Внутри — JSON со списком записей. Ключ выводится из отдельного пароля
пользователя через Argon2id, поэтому файл можно свободно переносить и хранить.

## Автоввод

`ui/autotype.rs` определяет окружение (Wayland или X11) по
`XDG_SESSION_TYPE` и выполняет последовательность в отдельном потоке:

- X11 — `xdotool type/key`;
- Wayland — `wtype - / -k`.

Последовательность разбирается на шаги: `{USERNAME}`, `{PASSWORD}`, `{TAB}`,
`{ENTER}`, `{DELAY мс}`, остальное — литеральный текст. Перед запуском
проверяется наличие вспомогательной утилиты: если её нет, пользователь
получает понятное сообщение, а не молчаливое бездействие.

## Интерфейс

- GTK4, окно верхнего уровня — `gtk::Window` с `HeaderBar` и
  `PopoverMenuBar` (меню строятся через `gio::Menu`).
- Состояние приложения — `Rc<AppState>` с базой (`RefCell<Option<Database>>`)
  и конфигурацией.
- Темы применяются через `gtk::CssProvider`; провайдеры сохраняются и
  удаляются при смене темы, чтобы не накапливаться.

## Конфигурация

`~/.config/taynik/config.toml` (путь берётся из `XDG_CONFIG_HOME`):

| Параметр | По умолчанию | Назначение |
|----------|---------------|-----------|
| `last_database` | — | последняя открытая база |
| `auto_lock_minutes` | 5 | автоблокировка, 0 — выключить |
| `lock_on_minimize` | false | блокировать при сворачивании |
| `clipboard_clear_seconds` | 45 | очистка буфера обмена, 0 — выключить |
| `theme` | `system` | ключ темы оформления |
| `autotype_sequence` | `{USERNAME}{TAB}{PASSWORD}` | последовательность автоввода |

## Тестирование

Модульные тесты (`cargo test`) покрывают:

- криптографию: round-trip, уникальность nonce, отказ при неверном AAD,
  детерминированность вывода ключа;
- репозиторий: создание/открытие, неверный пароль, **смена мастер-пароля с
  сохранением данных**, запрет подмены полей, резервная копия, удаление записи
  вместе с историей;
- TOTP: векторы RFC 2202, RFC 4231, RFC 6238 (SHA-1 и SHA-256), разбор
  `otpauth://`;
- генераторы: длина, обязательные символы, исключение похожих, отказ от
  некорректных параметров, размер словаря;
- CSV: round-trip, параметры TOTP, разные записи булева значения;
- зашифрованный экспорт: round-trip, отказ при неверном пароле, отсутствие
  открытого текста в файле;
- аудит: поиск слабых, повторяющихся и устаревших паролей.

Тесты используют облегчённые параметры Argon2id (8 МиБ, 1 итерация) — полный
KDF занимает секунды и делает набор тестов медленным.
